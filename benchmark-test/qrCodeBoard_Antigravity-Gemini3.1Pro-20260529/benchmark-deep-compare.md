# ⚖️ 벤치마크 딥 다이브 최종 통합 보고서 — QR코드 게시판

> **대상:** qrCodeBoard_Addy vs qrCodeBoard_TheScripture  
> **환경:** Antigravity IDE (단일 세션 / 자동승인)
> **모델:** Gemini 3.1 Pro (High)
> **기준:** F드라이브에 생성된 최신 소스 코드 (2분 vs 6분 산출물)  
> **목적:** 두 AI 에이전트 방법론의 실제 소스 코드 팩트(구현 여부)를 전수 검증하여 비교 분석

| 제외 | Addy | TheScripture |
|:---|:---|:---:|

| **수동 글쓰기 기능** | ❌ 텍스트 입력 폼은 있으나, 메인 페이지 스캔 연동용 | ❌ **글쓰기 버튼 아예 없음** (스캔 결과 뷰어로만 작동) |
| **결함의 원인 (AI 심리)** | "홈페이지와 게시판을 굳이 나눌 필요 없이 한 화면에 합치자" (편의적 해석) | "스캔해서 띄운다"는 동사에 너무 갇혀 할루시네이션 방지에 집착하다 일반 게시판의 필수 UX 누락 |

**분석 노트 (소스 검증 결과):**
1. **Addy의 편의주의 (게시판 증발):** 소스를 보면 `app.get('/')` 하나만 존재하고, `/board` 라우트는 아예 없습니다. 메인 페이지 하단에 `Recent Scans`라는 컴포넌트로 때웠습니다. 명시적인 "게시판 1개" 요구사항을 위반했습니다.
2. **The Scripture의 강박증 (글쓰기 증발):** 소스를 보면 `/board` 라우트에 게시판 화면은 잘 구현되어 있으나, 데이터는 오직 홈 화면의 카메라 스캔(`POST /api/scan`)을 통해서만 들어옵니다. 할루시네이션(임의 기능 추가)을 막으려는 방법론의 룰이 너무 강력하게 작용하여, 상식적인 게시판이라면 응당 있어야 할 **수동 글쓰기 버튼**마저 Scope 외부로 간주하고 날려버리는 기계적인 해석의 한계를 보여주었습니다.

## 9. 종합 평가 및 결론

두 에이전트가 단 2분, 6분 만에 생성한 소스 코드를 팩트 체크하여 대입해 본 결과, 놀라운 사실이 밝혀졌습니다.

### "속도의 대가로 생략된 아키텍처"
두 에이전트 모두 생성 속도를 극대화하기 위해 고급 아키텍처(서비스 레이어 분리, 라우트 분리, DB 고급 설정)를 **모두 생략(구현 안 됨)**하고 하나의 파일(`index.tsx`)에 코드를 쑤셔 넣는 Monolithic 구조를 택했습니다. 

### Addy의 강점과 치명적 약점
- ⚡ 2분 만에 시각적으로 그럴싸하고 컴포넌트가 분리된 UI를 뱉어냈습니다.
- ❌ 그러나 스캐너 자바스크립트 라이브러리(`html5-qrcode`) 자체를 **완전히 빼먹는 치명적 버그**를 남겼고, 명시된 "게시판 분리" 요구사항을 어겼으며, 예외 처리가 없어 서버 크래시 위험에 노출되었습니다.

### TheScripture의 강점과 치명적 약점
- 🛡️ 6분을 쓰면서 Monolithic 구조를 취했지만, DB 무결성(`CHECK`) 방어, `try-catch` 전역 래핑에 따른 서버 크래시 방어, 그리고 4개의 통합 테스트만큼은 끝끝내 지켜냈습니다.
- ❌ 그러나 17자 요구사항에 너무 교조적으로 얽매인 나머지, 상식적인 게시판의 필수 요소인 **'수동 글쓰기 버튼'마저 할루시네이션으로 취급해 삭제해버리는 기계적 맹점**을 보여주었습니다.

### 최종 트레이드오프 결론
단기간에 코드를 뽑아내는 환경에서, 일반 AI는 **'예외가 발생하든 말든 일단 눈에 보이는 UI 위주로 찍어내는 경향'**을 보인 반면, The Scripture 방법론은 **'디자인과 아키텍처 확장을 보류하더라도 서버가 죽지 않고 데이터가 보존되는 백엔드 방어선만큼은 코드로 증명해 내는 성향'**을 입증했습니다.
